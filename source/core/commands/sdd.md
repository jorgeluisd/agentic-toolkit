Orquesta el pipeline definido en `{{PLUGIN_ROOT}}/{{ORCHESTRATOR}}` para:

$ARGUMENTS

Reglas de orquestación:
1. Lee `{{ORCHESTRATOR}}` del plugin y el `{{CONTEXT_DOC}}` del proyecto antes de lanzar nada. Resuelve la **raíz de artefactos** (§0 del `{{CONTEXT_DOC}}` o `{{CONFIG_FILE}}`; default `docs/sdd/`) y úsala en todo el pipeline: donde este comando dice `docs/sdd/`, va la raíz resuelta. Si el store configurado es `engram`, comprueba que tengas herramientas de memoria disponibles en esta sesión: si no las tienes, degrada a `local`, dilo en una línea y sigue (§3 de `ORCHESTRATOR.md`). No abortes por esto.
2. Clasifica el nivel (`full` | `bugfix`), crea `<raíz>/<NNNN>-<slug>/` (NNNN = siguiente correlativo ignorando `_archive/`; slug = el de la rama), escribe el nombre en el puntero de la feature activa, `$(git rev-parse --absolute-git-dir)/sdd-current` (uno por worktree; fuera de git, `<raíz>/.current`), y el nivel en `<raíz>/<NNNN>-<slug>/.level`. El `.level` no es decorativo: el gatekeeper lo lee para saber qué insumos exigir, y si falta asume `full`.
2a. En layout lite (`SDD_LAYOUT`, default `lite`) creas en la carpeta `feature.md` con el encabezado y `## Log` → `L1 <fecha> humano (textual): > <pedido>`, copiando el pedido **tal cual** lo escribió el humano, sin resumir. Sin `L1` el gatekeeper no deja lanzar ninguna fase. Cada corrección posterior del humano va textual como `L2`, `L3`…
2b. Antes del `designer` (lite) o del `spec-writer` (classic), lista `<raíz>/specs/` y pásale al agente el spec de la capacidad que la feature toca, si ya existe: las specs nuevas declaran el delta contra ese comportamiento, no lo redefinen desde cero.
3. Lanza cada agente como agente aparte con un **handoff por referencia**: `Spec: <ruta>/feature.md (lee hasta ## Log). Haz T3; S2, S4.` — nunca el historial de esta conversación, una paráfrasis del pedido ni el cuerpo de un artefacto (`ORCHESTRATOR.md` §5.2; el gatekeeper deniega prompts de más de `SDD_HANDOFF_MAX_CHARS`). No lanzas un agente si falta su insumo. Si esta sesión no puede lanzar agentes aparte, sigue `{{PLUGIN_ROOT}}/ORCHESTRATOR-solo.md`: mismas fases y mismos gates, ejecutados en secuencia por ti.
4. Nivel `full` (default), layout lite: explorer → proposer (solo si `## Exploración` dice `DECISIÓN: sí`) → designer → **GATE 1** → implementer por tarea (strict-tdd si `TDD: ON`) → `bash {{PLUGIN_ROOT}}/hooks/review-plan.sh` → revisores según el riesgo (`ORCHESTRATOR.md` §5.1: en bajo, code-reviewer con `model: sonnet`; en alto, dos code-reviewer a ciegas + security-reviewer) → `{{CMD_PREFIX}}pr-draft` → **GATE 2** → (merge) → archiver. Layout classic: explorer → proposer → spec-writer → designer → task-planner → **GATE 1** → lo mismo.
   Nivel `bugfix`: explorer (escribe `## Specs` con `S1` = la reproducción y `## Tasks`) → implementer (TDD ON, el test que reproduce el bug es el RED) → verifier ∥ code-reviewer → **GATE 2**. Si aparece cambio de contrato o esquema, o el cambio deja de pasar el test de reanudación (`ORCHESTRATOR.md` §2), sube a `full`.
5. En cada gate te detienes, muestras el checklist de `gates/gate-N-*.md`, pides el token (`acepto` en GATE 1) y **registras la decisión en `gates.md`** antes de continuar. Sin registro, no continúas.
6. Un FAIL del verifier o un hallazgo alto del code-reviewer vuelve al implementer como tareas nuevas; nunca llega al GATE 2.
7. Git: tras el GATE 1, si la sesión está en la rama base, creas `feat|fix|chore/<slug>` desde ella (`git switch -c`) sin preguntar. El `implementer` commitea solo, un commit por tarea con verificaciones verdes (skill `delivery-workflow` §4). Push, PR y merge no los haces por iniciativa propia: el push a la rama de feature y la apertura del PR los autoriza el humano en GATE 2; el merge lo hace el humano. **Con `SDD_AUTONOMY=auto`:** antes del GATE 2 corres `bash {{PLUGIN_ROOT}}/hooks/gate2-auto.sh`; si sale 0, pusheas la rama, abres el PR con `{{CMD_PREFIX}}pr-draft` sin pedir confirmación, mergeas hacia la rama base con la estrategia de `delivery-workflow` §6 y lanzas el `archiver`; si sale 1, muestras sus motivos y el GATE 2 es humano. Nunca mergeas un release desde la rama base.
8. Si un insumo falta o una duda bloquea, paras y preguntas; no inventas.
